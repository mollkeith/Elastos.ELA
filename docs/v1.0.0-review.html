Elastos.ELA v1.0.0

A reviewer's guide to every change in the recovery release. 132 commits, 89d707d0..35bc98ef, all of them listed here. Two documentation commits, this page and the changelog, sit on top of that range.

This page exists so that a reviewer can understand what changed and why without reading the diff. Each significant commit answers three questions: what was wrong, what changed, and what it means for someone running a node. Routine commits get a line. Nothing is left out, and the index at the end lists all 132 short hashes so you can check that for yourself.

Where the baseline is

This branch begins at released v0.9.9.6, c61c9e61, which is what node operators are running today. The commit directly above it, 89d707d0, carries the v0.9.9.7 development snapshot that the recovery work was based on. That snapshot arrived as a squashed tree rather than as history, so it is recorded as a single commit. v0.9.9.7 was never released and no such tag exists upstream.

Everything described on this page is the delta against that snapshot, not against v0.9.9.6. The distinction matters: everything that arrived inside the snapshot, including gate 1 itself, the CrossChain-UTXO freeze heights, the forced-rollback height and trigger and the frozen-address list, is not attributed by this page. A release that supersedes v0.9.9.6 must not imply otherwise.

The middle section, between released v0.9.9.6 and the snapshot, is not ours and we have not audited it. It is roughly 40 files. This branch makes it directly readable as git diff c61c9e61 89d707d0, which is more than the canonical working clone could offer, because that clone has no upstream history in its object store. No in-tree document of ours covers those files. It is one of the two places we consider ourselves weakest, and fresh eyes on it are worth more than fresh eyes on anything we wrote.

The changes that matter, explained

Fifteen items, in the order a reviewer needs them. Each one names its class, states the defect, gives the measurement behind it, and says what it would have meant for someone running a node. Where something is inferred rather than proven, it says so in those words. Every item links to its commit entry further down. Two coordinated mainnet heights are referred to throughout, gate 1 at 2,260,451 and gate 2 at 2,265,000; the next section sets them out.

The restart itself

1. A resumed rewind left the store height stale, so the node could never accept the first block of the chain it was rolled back for

Would have broken the restartMost serious single finding

The defect

The chain store height is lowered only inside the per-block rollback transaction. A rewind that was interrupted and then resumed correctly skips any block an earlier run already committed. When the block it skipped was target plus one, block 2,260,451, nothing lowered the height at all. The rewind finished with a rewound block index and a store height still describing the chain it had just discarded.

The evidence

Found by an external review of the forced-rollback machinery and confirmed on this tree. handlePersistBlockTask then rejects the recovered chain's replacement block at that height. Five defects on this path were confirmed and fixed in the same commit, and three further claims were checked and deliberately not fixed. The fix is pinned by fail-on-pristine tests, with 12 of 12 mutants killed.

What it means

2,260,451 is the first block of the recovered chain. It is the one block the node has to accept. A node in this state comes up looking recovered, rejects that block, and stops following the fleet. Getting there needs an interrupt during the rewind and a restart, which is exactly the case the crash-atomic work exists to support, so this defect and item 3 sit on the same path.

Limits

The evidence is a fail-on-pristine test against the production rollback path. No live multi-node rehearsal of interrupt, resume and rejoin is recorded.

Commit 587ca7b3, on top of aa04d0f2.

2. The rollback trigger was compared in the wrong byte order, so the rewind would never have fired on mainnet at all

Would have broken the restartInherited, not from this range

The defect

ForcedRollbackTrigger is configured in display byte order, the order an operator reads off a block explorer. Block hashes are stored internally in the reverse of that order. Parsing the configured value without reversing it, then comparing it to the stored hash, gives a comparison that can never be true. ForcedRollbackArmed returns false, and it is a pure predicate that deliberately does not log, so the node starts on the exploit chain and says nothing.

The evidence

The trigger is e1a11e04…2ea9af in display order and afa92e8c…a1e1 internally. The correct parse is Uint256FromReversedHexString, and the wrong one is the ordinary Uint256FromHexString sitting next to it in the same package. The Elastos core engineers confirmed the fix as Q-B4, recorded in 94690f3e.

What it means

With the wrong parse the whole recovery is inert. Every node boots, declines to rewind, and stays on the chain this release exists to leave, with no error anywhere.

Limits

This fix is not in 89d707d0..HEAD. It arrived inside the squashed snapshot, so this page does not attribute it, for the reason given at the top of the page. What the release adds is that the boot path's store probe, LocateForcedRollbackTrigger, parses the trigger through a single helper that carries the failure mode in its own comment (815d38d4).

3. The rewind was not crash atomic, and an interrupted one eventually booted clean looking with the exploit block still in the store

Would have broken the restart

The defect

The per-block rewind ran three database transactions in the order DBRemoveBlockNode, RollbackBlock, DBRemoveBlockFromStore. The first destroys the header row that the block index is rebuilt from at startup, and that index drives both the arming condition and the bound of the rewind. A crash between the first and the second erased the evidence that the work was unfinished.

The evidence

Measured on this tree with the middle step forced to fail. The node ratcheted 6, 5, 4, 3, 2 across four restarts, then came up reporting itself recovered with every discarded block still main-chain indexed, while the residue cleaner purged 0 of 4.

A second defect on the same path: ForceRollback logged "persisted store verified clean" while it was describing ffldb's 20 MiB, 300 second write cache. A copy of the data directory taken at the instant that line printed still held all four rewound blocks main-chain indexed, with best state at the pre-rollback tip.

What it means

Power loss during the rewind used to produce a node that reports success and is still on the exploit chain. The order is now RollbackBlock, DBRemoveBlockFromStore, then the header row, so the header row is the durable resume marker and an interrupted rewind is retried once per block on the next boot. The census flushes before counting and the rewind flushes after clearing its marker, so the completion line now means the bytes are on disk. Progress output goes from about 2 lines to about 20, with elapsed time, so a long rewind no longer looks hung.

Limits

Interrupts are handled on block boundaries. The boot check that catches a disarmed, unfinished rewind can only refuse on evidence this binary wrote, so it cannot rescue a node that was interrupted under an older build.

Commits aa04d0f2 and eb4a3cd3.

4. A rolled-back node still served the exploit block by hash

Changes real behaviorResidue #2

The defect

ForceRollback removed the header index, the height indexes and the tx-index siblings. It never removed the by-hash location entry in the ffldb bucket ffldb-blockidx, driver bucket id 0x00000001. That bucket is the single persistent chokepoint every by-hash serve path reads, which is RPC getblock and P2P getdata.

The evidence

Fail-on-pristine against a real ffldb-backed store: the pristine build serves the discarded heights by hash, the patched build returns ErrBlockNotFound, and heights at or below the target are still served by both, so nothing is over-deleted. The exploit block carries its original 25-vote confirm inline.

A follow-up found the sweep walked only the accepted main chain. The real mainnet store holds exactly one above-target block that never joined the best chain, c34b71f2… at header height 2,260,595. Measured residue above the target went from 1 to 0.

What it means

A recovered node would have handed the exploit chain back to any peer that asked for it by hash, over RPC and P2P, indefinitely. The manual ela-cli rollback path carried the same residue. A node that already rewound under an older build needs ela-cli purgeresidue once, with the node stopped.

Limits

The flat-file bytes are left orphaned by design. A bounded one-block crash window remains between the rollback transaction and the purge, backstopped by the offline cleaner. If you compare data directories against a keystone baseline, bucket 0x00000001 now legitimately differs by exactly the discarded keys, and that delta must not be read as rollback failing to equal forward.

Commits 0430082d, b7c229cc, b4fc1949, 61b43601.

5. Our own money-range bound was ungated and rejected a real historical block

Would have broken the restartRelease blocker

The defect

The money-range bound on CrossChainOutput.Validate() was ungated, and OutputPayload.Validate() carries no block height, so the bound applied to every transaction at every height. Mainnet block 2,208,265 holds a TransferCrossChainAsset that released v0.9.9.6 accepted and DPoS finalized, declaring a target amount of 92,233,720,368.54765808 ELA.

The evidence

Measured before the fix: validation returns "target amount out of money range" at height 2,208,265 and replay halts there, on a block every existing node already accepted. That block sits 52,185 blocks below the forced-rollback target, so it stays on the canonical chain.

The same line also overflowed. Blocks 2,208,257 and 2,208,265, 638 seconds apart on 2026-05-08, same signer, same EVM target, each declared a target amount of int64max - 9999. Adding the 10,000 fee gives exactly 2^63, which wraps negative, so the comparison became 199980000 < -9223372036854775808, which is false, which means accepted. That is 92.2 billion ELA declared against 1.9998 ELA locked, 2,238 times the entire ever-creatable supply.

What it means

Shipped as it stood, a v1.0.0 node could not sync the chain from genesis. The bound moves to the one caller that knows the height and is gated at gate 1. Below the gate the original expression is preserved exactly, wrap and all, so retained history is byte-identical. The tests drive the production dispatch with the real 270-byte mainnet transaction decoded from its on-chain bytes, and the boundary is exact: accepted at 2,260,450, rejected at 2,260,451.

Limits

Whether ESC credited the 92.2 billion ELA declared against the real custody address is not established. At ESC head that target has balance 0, nonce 0 and no code on both public nodes, which is strong evidence it did not, but neither node retains state from that height. Under the standing rule that mint findings are proven and never inferred, that question stays open.

Money

6. An invented asset could have become real ELA

Changes real behaviorGate 1Gate 2

The defect

Two halves of one assumption, that the money rules were ELA-only. CheckTransactionOutput demands core.ELAAssetID on every output only below PublicDPOSHeight, so the branch taken by every block since 402,680 has no asset rule at all, and checkCoinbaseTransactionContext pins the reward values and most of the addresses but never the asset. The output is then indexed as an ordinary spendable UTXO.

On the other side, the DPoS reward state kept summing the asset-blind tx.Fee() over every transaction. That state is the side that mints, because accumulative reward feeds the round reward, which becomes claimable ELA. A producer spending a self-issued non-ELA UTXO worth V could hand-craft a coinbase that passed every check and mint ceil(0.35 * V) of unbacked ELA, repeatable every block.

The evidence

A census of all 41,368,277 retained outputs found zero non-ELA outputs. A full scan of 2,260,597 retained blocks found zero outputs carrying a non-ELA asset id, ever. RegisterAsset is banned at and above gate 1, and its own double spend was reproduced 6 times against a real unspent index, so the precondition is structurally unreachable going forward. Below-gate replay safety was proven by differential equivalence against the pristine expression over 60 combinations of height and asset arrangement, not by census alone.

What it means

The coinbase asset rule comes back at gate 1, per-asset conservation is enforced, and one authoritative ELA-only fee feeds both the validator and the reward state. No honest block changes, because on an all-ELA chain the two bases are identical.

Limits

Ordering matters and is stated in the commit. Moving to the strict fee alone would have been a regression, because the asset-blind aggregate was, by accident, the only bound on how much foreign-asset value a transaction could emit, so the negative-fee fix has to ship with it. The reward-basis half is classified dormant by measurement, not closed by argument.

Commits ac3f4495 and 40b0d2b1, with proofs in cea50534 and a5d43361.

10. The once-only property was proven rather than built

Property, not machinery

The question

A one-shot destructive operation has to be one-shot. The usual way to get that is a flag or a marker, which is more state that can be wrong, and more state an operator can clear by accident.

The evidence

Arming requires the block at target plus one to hash to the trigger, and the rewind is exactly the operation that removes that block. The condition that authorizes the rewind is falsified by the rewind. Proven by executing three consecutive boots plus a re-mine at target plus one.

What it means

Nothing was added to carry the property, so there is nothing extra to corrupt or to disarm. The one boot on which the rewind does fire a second time, a restored pre-rollback backup, is correct behavior, and the node now states why it is firing.

Limits

That test passes on the pristine tree, deliberately. It pins a property the code already had rather than demonstrating a defect, which is the opposite of the standard applied everywhere else in the release.

12. DPoS networking started before the node validated its own state

Changes real behaviorNo acceptance change

The defect

In main.go, chain.Init runs at line 293, arbitrator.Start at 364 which brings the DPoS peer-to-peer mesh up, InitCheckpoint at 406, and only then at 440 the refusal that compares the restored CkpManager.MaxHeight against the rewind target. 1. Recovery machinery

18 commits. The forced rollback is how the fleet leaves the exploit chain. This section makes the rewind crash-atomic, makes its claims about disk true, stops a node that did not complete it from quietly joining the recovered network, and gives an operator a way to find all of that out before starting anything.

Defect

The evidence standard

Three rules were applied consistently, and they explain why several commits in this release contain no production code at all.

1. Fail on pristine

A test that passes on the unfixed tree proves nothing. Every test that claims to demonstrate a defect was run against the pristine tree first and had to fail there.

Two commits in this release exist purely because a test did not meet that bar: 0734014d replaced an F-131 test that passed on pristine with one that drives the real harm, and e971b04c rewrote six tests that all passed against three broken variants of their own fix, because every fixture started in the state the fix produces.

2. Mutation testing, and specifically call-site mutation

The harder failure is a test that is correct about a helper while nothing in production calls that helper. This release found that condition twice at scale.

380cfd63 measured it first: 10 of 17 wiring mutations severed a live production guard with the entire suite green. It answered with 19 files that each fail when the production call site is removed, and 45 of 45 production mutations discriminated.

8799429e then ran a semantic-neuter battery over the guards this campaign introduced. Rather than deleting syntax, it rewrites if C { as if false && (C) {, so the build stays honest and a green suite means the test genuinely does not discriminate. 256 mutations, 252 guard sites, 94 killed, 158 survived. 17 of those survivors are closed there. The rest are reported, not hidden.

The general rule that came out of both: every test must drive the production dispatch, never an internal helper. Where that is genuinely impossible, as with F-052, the test asserts instead that the guard's error is consumed by an unweakened check that returns.

3. Proven, inferred, refuted, deferred

Every claim in this release carries one of four labels, and they are not interchangeable.

ProvenDemonstrated by execution against real data or a real store, and reproducible.F-015 driven on a live rehearsal chain (8cc3743a); F-059 master-key recovery 6 of 6 (5f8906f9); the 89 byte-identical reward pairs in blocks 435,243 and 435,244.

The standing rule behind this is specific to supply: inflation and mint claims are proven empirically or they stay labeled deferred. What "measured" means in the entries above

Wherever an entry gives a census figure, it comes from a read-only scan of the retained chain with the production codecs, usually all 2,260,597 blocks. Where a fix could in principle reject a real historical block, the standard evidence is a pair: the production check with its gate forced to zero must reject zero retained blocks, and a positive control must show the check rejecting synthetic violations that canonical accepts. c5af886f is the clearest example, at 0 of 2,260,597 and 2,310 of 2,310 respectively.
